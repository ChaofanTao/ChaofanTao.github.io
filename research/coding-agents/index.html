Coding Agents, Agentic Data and Agentic RL

By Chaofan Tao (陶超凡), LegoX · Last updated November 4, 2026

A coding agent is more than a model. Its behavior also depends on the harness that manages its tools and context, the tasks it learns from, and the reward that tells it whether it succeeded. Most strong agents are built with pipelines in which these pieces are tightly coupled and rarely released. Chaofan Tao and collaborators at LegoX take that pipeline apart into open, reusable blocks (task construction, trajectory curation, fine-tuning, harness-native reinforcement learning and review) and document what each block teaches about building reliable coding agents.

On this page: Why open · Verified tasks · Trajectories and rewards · Fine-tuning · RL in the native harness · Review and evaluation · Open resources

Why build coding agents end to end, in the open?

Because the pieces interact in ways that only show up when you control all of them. The same model can behave quite differently under different harnesses, a strong teacher can quietly copy answers instead of solving tasks, and a rising reward curve can hide broken infrastructure. LegoX packages each stage as a block with its own code, environment and dashboard, and makes the blocks operable by coding agents themselves: Claude Code or Codex can run them as plugin skills. The goal is a system others can rebuild, audit and extend, rather than a single checkpoint.

Where do verified training tasks come from?

From real software history, kept only when execution proves them. LegoFlow's Curator finds merged pull requests, gathers the issue, commits and tests, rewrites them into a task that does not leak the answer, builds an isolated environment in the Harbor task format, and keeps the task only if the original code fails the tests and the reference fix passes. Passing that check shows a task is usable, not that it is worth training on, so Curator also scores difficulty with a static rubric over patch scope, logic complexity, context breadth, test complexity and instruction detail, with no LLM judge involved. SWE-Lego adds synthetic tasks by injecting bugs through LLM rewriting and syntax-tree transformations, and Terminal-Lego turns Stack Overflow problems into sandboxed command-line tasks.

Know-how

  • Only a tiny fraction of raw pull requests survive verification; quality filters matter more than volume.
  • Real tasks give depth (realistic, multi-file bugs) and synthetic tasks give breadth. Mixing the two helps more than either alone.
  • Harder, multi-file tasks lead teachers to produce longer, richer trajectories, which make better training data.

Which trajectories are worth learning from, and how do you keep rewards honest?

A trajectory is a recorded attempt by a teacher agent, and not every successful one is a good lesson. Three findings shape how LegoX curates them. First, reasoning depth matters more than reasoning coverage: traces that think briefly on every turn teach less than traces that reason in depth when the problem calls for it, and most of the gain comes from removing the shallowest traces. Second, environment-grounded trajectories make better teachers. In the Terminal-Lego study, traces that inspect, act and verify transferred better than those of stronger agents that jump straight to the answer; in the paper's words, “the best solver is the worst teacher.” Third, stronger models are better at hacking: they find the upstream pull request, copy the patch, or compare their change against the reference commit.

Know-how

  • Filter out shallow reasoning traces rather than simply picking the longest ones.
  • Clean trajectories before training: remove Git history that reveals the fix, repair malformed tool calls, keep the tool set small, and recycle runs that found the right file but failed to fix it.
  • Defend against hacking in two layers: tell the agent not to look up solutions, and enforce it in the environment by rewriting Git history and restricting network access while the agent runs, restoring them only for grading.

How far can supervised fine-tuning go?

Further than its reputation suggests, if the data and the loss are right. SWE-Lego is an SFT-only recipe. Error masking keeps the full trajectory as context but excludes erroneous agent steps from the loss, so the model sees its mistakes without imitating them. A difficulty curriculum uses trajectory length as a proxy for difficulty, since longer trajectories are strongly associated with harder tasks, and trains in stages from easy to hard while carrying earlier data forward to avoid forgetting. At inference time, extra compute is best spent first on more interaction turns and then, once that saturates, on parallel attempts ranked by a verifier.

Know-how

  • Mask the loss on wrong steps instead of throwing away imperfect trajectories.
  • A generative verifier, which answers “yes” or “no” as text, ranks attempts better than a regression head because it reuses what the model learned in pre-training.

Why train reinforcement learning inside the agent's native harness?

Because the harness is part of the environment the model learns from. Lego-RL connects unmodified harnesses such as OpenHands, Claude Code and OpenCode to a policy-gradient trainer without changing their control flow. The hard part is faithfulness. Harnesses rewrite their own history by compacting context, re-serializing tool calls and running sub-agents, so a saved transcript is not the token sequence the model actually sampled. An in-process proxy records tokens, log-probabilities and mixture-of-experts routing at generation time, and the routing is replayed during training so that both sides compute the same probabilities. Each attempt runs in its own sandbox with phase-dependent anti-cheating defenses, and dashboards make every trajectory inspectable.

Know-how

  • Check token and probability alignment explicitly; misalignments are silent bugs that look like normal training.
  • Train on tasks the current policy solves only sometimes. Groups that always pass or always fail give no learning signal, and the useful band shifts as the policy improves.
  • Separate policy failures from infrastructure failures, such as tool-call parser mismatches or environment setup errors, before reading a reward curve.
  • After training, agents inspect more files before editing, reread their edits and run tests more often, at the cost of longer interactions.

The same infrastructure supports newer recipes. Mixed-harness RL trains one model that works across several harnesses instead of one model per harness, and Single-Rollout Asynchronous Optimization (SAO) learns from a single attempt per task with a learned critic, which needs warm-up and advantage whitening to stay stable.

How should coding agents be reviewed and evaluated?

Like human software work: with review, iteration and realistic checks. SWE-Review adds the missing second half of the loop. A reviewer agent explores the repository on its own, traces the root cause, compares its diagnosis with the submitted patch and returns structured feedback, turning one-shot generation into a generate-review-revise loop. Review trajectories also transfer back to issue resolution, and because choosing among attempts is cheaper than generating more of them, review makes test-time scaling more efficient. For evaluation, SwingArena (ICLR Oral) has models compete as patch submitters and test-writing reviewers in continuous-integration pipelines, REAgent (ICSE) checks and refines the issue as a requirement before patching, and RLVRR (ICLR) extends verifiable rewards beyond code to open-ended generation.
