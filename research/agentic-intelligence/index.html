Agentic Intelligence

An agent's ability doesn't live in the model alone. It lives in the loop around it: seeing the situation, acting, learning from what happened, and being checked. At LegoX we have been building that loop in the open for coding agents, and our multimodal work tests what it needs beyond code. This page walks through what we found, and shares some thoughts on where the loop goes next.

By Chaofan Tao (陶超凡) · Last updated November 9, 2026

For a long time, progress in AI meant a better answer to a fixed question. Agents change the question. An agent has to notice the detail that matters, decide what to try, act, read what came back and adjust. Each of those steps can fail on its own, and each needs its own kind of evidence: whether the model saw the right thing, whether its actions were grounded in what the environment showed it, whether it learned the right lesson from an attempt, and whether we can trust the check that says it improved.

Coding agents are where we study all of these at once. Code leaves a record of every action and every result, and tests give an outcome you can verify. At LegoX, we build each part of this loop as open, reusable pieces: how verified experience is collected, how it becomes training signal, and how the result is checked. Our multimodal work asks the same questions where the environment is an image, a video, the web or a robot.

1. Coding agents as a laboratory

A coding agent never sees a repository directly. It sees whatever its harness shows it: which files and tool outputs reach the context, when history is compacted, how errors are reported, what happens after a command fails. When we trained the same starting model inside three widely used harnesses (OpenHands, Claude Code and OpenCode) with Lego-RL (arXiv 2026), it already behaved differently in each before any training. The harness is part of the environment, not plumbing around the model. That observation shaped how we collect data, how we train, and how we check results.

Data: experience worth learning from

LegoFlow (LegoX blog, 2026) treats code-data engineering as a chain of blocks. Curator finds merged pull requests, gathers the issue, commits and tests, rewrites them into a task that does not leak the answer, builds an isolated environment and keeps the task only if the original code fails the tests and the reference fix passes. Because passing that check only makes a task usable, Curator also scores difficulty with a static rubric over the size of the patch, the logic it adds, how much of the codebase it touches, the tests and the detail of the instructions, with no LLM judge involved. Tracer rolls out trajectories in sandboxes and screens them, and Trainer and Evaluator close the loop. Every block is packaged as a plugin skill, so a coding agent such as Claude Code or Codex can run the pipeline itself, and each block has its own dashboard. In one experiment, an agent ran the whole pipeline end to end, read the evaluation, noticed that many teacher traces contained only shallow reasoning, changed the filter and trained a clearly better model in the next round.

SWE-Lego (arXiv 2026) combines real tasks from resolved pull requests with synthetic ones created by injecting bugs, through LLM rewriting and syntax-tree transformations. Real tasks bring depth and realism; synthetic tasks bring scale, and for the same repositories, adding them keeps helping. Terminal-Lego (arXiv 2026) brings the same discipline to command-line work, turning Stack Overflow problems into Docker-verified tasks.

The lessons that mattered most were about which trajectories to keep. Terminal-Lego found that the strongest solver is not necessarily the best teacher: traces that visibly inspect, act on what they found and then verify the result teach students better than traces from stronger agents that jump straight to the answer. LegoFlow found that reasoning depth matters more than coverage. Teachers that think a little on every turn teach less than teachers that think hard when the problem calls for it, and most of the benefit comes from removing the shallowest traces rather than keeping only the longest. SWE-Lego added practical cleaning rules: repair malformed tool calls, keep the tool set small, and recycle attempts that found the right file but failed to fix it.

Experience also has an honesty problem. Stronger teachers are better at finding shortcuts: locating the upstream pull request, copying the patch, or reading the fix from Git history. A successful trajectory is not necessarily an honest one. What worked was two layers: tell the agent plainly not to look up solutions, and make it impossible anyway, by rewriting Git history, hiding test files and restricting the network while the agent works, then restoring them only for grading.

Learning: turning experience into capability

SWE-Lego showed that plain supervised fine-tuning can produce a strong open coding agent when the loss gets as much care as the data. Error masking keeps the whole trajectory, mistakes included, in context but takes no gradient on the wrong steps, so the model learns from its errors without learning to repeat them. A curriculum uses trajectory length as a stand-in for difficulty and trains from easy to hard, carrying earlier data forward. At inference time, extra compute is best spent first on more interaction turns and, once that saturates, on parallel attempts, with a verifier that answers "yes" or "no" in text choosing among them better than a scoring head does.

For reinforcement learning, Lego-RL trains inside the real, unmodified harness. The hard part is making sure the trainer sees what the agent actually did. Harnesses rewrite their own history by compacting context, re-serializing tool calls and running sub-agents, so a saved transcript is not the token sequence that was sampled. An in-process proxy records tokens, probabilities and mixture-of-experts routing at generation time, and the routing is replayed during training. Mismatches here make no noise: training runs and curves move, which is exactly why they have to be checked explicitly. Two more lessons came from the runs themselves. Tasks the model always or never solves teach it nothing, so the useful difficulty band has to follow the policy as it improves. And a falling reward can mean a broken parser or failed environment setups rather than a worse policy, so dashboards that break down how every attempt ended are part of the method, not an extra. After training, the agents read more code before editing, reread their own edits and run tests more often, at the cost of longer sessions.

Two follow-ups extend the recipe. Training one model on a mix of harnesses (LegoX blog, 2026) came close to the average of separately trained models while narrowing some of the gaps between harnesses. Single-rollout optimization (LegoX blog, 2026) learns from one attempt per task with a learned critic instead of comparing many attempts, which saves most of the sampling but only works once the critic has been warmed up and the advantages normalized; without that, the policy collapsed into repeating its "think" tool. For tasks without a single checkable answer, RLVRR (ICLR 2026) builds a chain of rewards from good reference answers, covering content and style, and OVD (arXiv 2026) learns from a teacher's text feedback on the student's own partial attempts, keeping good beginnings and replacing weak continuations.

Checking: review and evaluation

SWE-Review (arXiv 2026) trains a reviewer agent that explores the repository on its own, works out the root cause, compares it with a submitted patch and writes structured feedback, turning one-shot generation into generate, review and revise. Two results matter beyond the paper: review data also makes models better at fixing issues, and because choosing among a few attempts is cheaper than producing many more, a good reviewer makes test-time compute go further. SwingArena (ICLR 2026 Oral) puts models into a continuous-integration loop as both patch submitters and test-writing reviewers across several languages, and REAgent (ICSE 2027) checks and improves the issue description itself before any patch is written.

2. Beyond code: multimodal reasoning and the physical world

Code is a forgiving environment: everything is text and every result can be checked. Our multimodal work asks what the loop needs when the agent has to look. In NAVERO (arXiv 2024), we found that video-language models often can't tell who did what to whom, matching a video to a caption even when the action or relation is wrong; training on such near-miss descriptions taught the model to separate similar actions. PhyX (TMLR 2026) shows models answering physics questions about images from memorized formulas and surface patterns rather than understanding the situation. MMSearch-Plus (ICLR 2026) builds search tasks whose answers depend on small visual clues carried through several rounds of retrieval; tools to mark, crop and zoom change what the agent can find, and most failures come from not locating the right evidence rather than from the last reasoning step.

On training, the synergy dilemma (TMLR 2025) study found that long chain-of-thought SFT and RL help reasoning VLMs in different places, and that combining them tends to trade one benefit for the other. SRPO (NeurIPS 2025) first shows the model what a useful reflection looks like, then rewards reflections that actually change its reasoning. RoboCodeX (ICML 2024) turns instructions into object-level actions with grasping and safety constraints written as code, so code plays for a robot the role a harness plays for a software agent. Our survey of autoregressive models in vision (TMLR 2025) maps how visual generation and understanding are converging, and its paper list has become a widely used reference. Across these projects, the failure usually starts before the reasoning, at seeing the right detail or finding the right evidence, which is the part of the loop that agents, unlike fixed models, can go and fix.

What we learned

  1. The strongest model is rarely the best teacher. What transfers is behavior the student can see and imitate: looking, acting on what was found, checking. The same mismatch between teacher strength and student learnability shows up in our distillation work.
  2. Reliable judgment is the scarce resource. Verified tasks, verifiers, reviewers and CI-based arenas are all ways of producing judgments we can trust. Generating attempts is cheap; choosing between them reliably is what scales.
  3. The trainer must see what the agent actually did. In agent RL, systems details such as token alignment and routing replay decide whether learning optimizes the right thing.
  4. Stronger agents find more shortcuts. Git history, upstream patches, visual questions answerable from text alone: honesty has to be built into the environment and the benchmark.
  5. Depth beats coverage. Careful reasoning where it is needed, useful reflection over long reflection, and evidence over verbosity.

Some thoughts on the future

These are personal views. Each grew out of something we ran into in the work above, and each is, in a sense, a larger version of a problem we have already met in small form.

Very long-horizon agents: from hours of work to weeks

Fixing one issue takes an agent minutes to hours. Building a product feature, migrating a large codebase or running a research project can take weeks of steady work, and I think that is where agents are heading. At that length, several things we saw in small form become the main problems. The goal itself drifts: REAgent showed that a vague issue description leads agents astray even on short tasks, so a week-long task will need to revisit its own requirements as it goes. A single pass or fail at the very end is far too little feedback, so progress has to be checked at milestones, the way SWE-Review checks a patch before it is accepted. Credit becomes hard to assign; in single-rollout optimization, the critic's estimate of success tended to jump when new tool feedback arrived, which suggests that credit can be anchored to meaningful checkpoints rather than spread over every step. And over weeks, environments will break, so state has to survive failures, the same lesson behind Lego-RL's failure dashboards and our fault-tolerant serving work.

Memory ties these together. More experience is not the hard part; keeping the right part of it is. I think experience will have to be kept at three levels. Stable habits, such as checking your own edit, belong in the weights. Procedures, such as how to set up and verify an environment, belong in reusable skills and tools; LegoFlow's blocks are a small example. Task-specific facts belong in memory, and every entry should carry the conditions under which it was true: which data, which code version, which settings. My guess is that very long-horizon agents will be organized around milestones: at each one, the agent re-reads the goal, verifies its progress, writes down what it learned with its conditions, and saves its state.

Teams of agents: extra agents help only when they add independent evidence

It is tempting to scale agents by running more of them in parallel. Our review work suggests a more specific condition. SWE-Review works because the reviewer explores the repository on its own instead of re-reading the generator's reasoning, and SwingArena separates the agent that writes a patch from the agent that writes the tests. Two agents with the same context and the same assumptions tend to miss the same bug. So I think useful teams will be organized around a division of verification rather than a division of labor alone: a proposer, a tester and a reviewer that see different information, with shared memory that records evidence and provenance rather than just conclusions. Studies of why multi-agent systems fail point the same way: many failures come from unclear specifications, weak verification and agents not knowing when to stop.

Evaluation: it is becoming the main bottleneck, and it has to be treated like a security boundary

Every capability gain we saw came with a matching gain in the ability to exploit the environment. In LegoFlow, stronger teachers cheated more; in Lego-RL, we needed defenses at every phase of the sandbox; in multimodal benchmarks, questions could be answered without really looking. I expect this to get worse, not better. Benchmarks for strong agents need locked-down networks, clean re-grading of the final result, held-out tasks that are never used during development, and regular refreshes. Training rewards need the same care: a record should say whether an attempt failed, was never scored, or succeeded by a route we would not accept, because a pipeline that confuses these teaches the next model the wrong lesson.

AI for AI: if AI is to improve AI, judgment will be the weakest link

Systems such as AlphaEvolve show that AI can already propose and test improvements to algorithms and computing infrastructure. LegoFlow's agent-run iterations are a small instance of the same idea: an agent reads evaluation results, changes how training data is filtered, and the next model improves. What our experience says is that generating candidate improvements is the easy part; deciding which ones are real is hard. A self-improving loop should separate the information used to propose a change, to select it and to confirm it; keep fresh tasks that never took part in the search; and compare progress at the same total budget, so that "better" does not just mean "searched more". I also think the improvements most likely to compound are improvements to the loop's own tooling, its data pipelines, environments and verifiers, because each raises the quality of every later round.

AI for Science: the longest horizon, with the weakest verifier

Scientific discovery is, in a way, the hardest version of everything above: the horizon is months or years, the goal shifts as you learn, and there is rarely a unit test that tells you whether a claim is true. That is why I think the lessons from coding agents carry over almost directly, starting with verification. A science agent needs an environment where it can act and see real consequences: simulators, data-analysis sandboxes and, increasingly, programmable labs play the role a harness and a test suite play for code. AI for AI is moving first precisely because its "lab" is a compute cluster, where experiments are cheap to run and easy to check; physical sciences will follow as more of the lab becomes programmable.

Our own work touches several of the pieces. PhyX shows that today's multimodal models still lean on memorized formulas instead of physical understanding, which is exactly the gap that grounding in simulation and experiment should close. MMSearch-Plus is about tracing evidence to its source, which is the everyday work of reading literature and data. RLVRR builds rewards for open-ended writing, the form most scientific output takes. And our vocabulary scaling study trusted its conclusion only after three independent estimation methods agreed, a small example of the replication discipline a science agent should follow. The risk is also familiar: the scientific version of reward hacking is cherry-picking runs and over-fitting to one dataset. So I expect useful science agents to keep a record of every experiment they tried, not just the ones that worked, and to confirm findings on data and settings they never used while searching.

Open questions

  • Can an agent trained across several harnesses do well in one it has never seen? Our mixed-harness training only covered harnesses that were part of training, so it shows that skills can be shared, not that they transfer to new tools. Real deployments keep changing their tools.
  • How do we tell which steps helped when one result arrives after hours or days of work? The critic in single-rollout optimization hints that progress shows up at turn boundaries. Whether that is enough to assign credit across a week-long task is unclear.
  • How should a long task keep its goal right? REAgent improves the requirement before work starts, but in a long project the requirement itself changes. When should an agent stop and revisit it, and who confirms the new version is right?
  • What should go into weights, skills and memory? Habits seem to belong in weights and facts in memory, but procedures sit in between, and each choice behaves differently when the base model is updated.
  • How independent are two agents' checks, really? If two agents share a base model, they may share blind spots even with different context. We need ways to measure that, not just assume it.
  • How can a self-improving loop show that it got better at improving? Fresh tasks get used up over many rounds, and comparing at equal budget is expensive. We do not yet have a cheap, trustworthy way to measure progress in the loop itself.
  • What is the unit test for a scientific claim? Simulations can be gamed and real experiments are slow. Finding checks that are cheap enough to run often and hard enough to fool is, I think, the central problem for AI for Science.
