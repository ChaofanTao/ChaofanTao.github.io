Agentic Coding, Reasoning and Evaluation

After fixing one issue, can an agent keep working with the user until the project is complete? I see our work on agent training, data and evaluation as a starting point for that harder problem: understanding requirements, keeping track of evidence, and making progress as the task changes.

By Chaofan Tao (陶超凡) · Last updated November 6, 2026

Fixing a well-specified issue and building a project from a few sentences of requirements ask different things of an agent. The second involves deciding what to build first, how the pieces should fit, and which questions need the user's input. Requirements may change halfway through. Getting the latest code to run is one step; keeping earlier work useful is another.

I organize our related work around four questions: what environment the agent works in, what experience it collects, what training signal it receives, and how we evaluate the result. LegoFlow, SWE-Lego, Lego-RL and SWE-Review approach different parts of this process. Below, I explain what the experiments establish, then consider what is still missing for longer projects and sustained collaboration.

1. Changing the harness changes the problem

A harness connects the model to tools and an environment. It decides how files are read, how tool results are presented, when history is compacted, and what happens after a failed command. Each choice changes the evidence available for the model's next action.

Lego-RL's experiments give a concrete example. The same starting Qwen3.5-35B-A3B checkpoint scores 64.0%, 62.4% and 57.2% on SWE-bench Verified through OpenHands SDK, Claude Code and OpenCode. The surrounding execution loop matters to performance. That motivated training inside the existing harness, although the comparison alone does not establish that native training beats training in a rewritten harness.

Maintaining a separate model for each harness is cumbersome. We therefore tried mixed-harness training: one model learning through all three. Its average performance on the evaluated benchmarks approaches that of three separately trained and deployed models. All three harnesses participated in training, however. To distinguish a transferable way of working from adaptation to familiar interfaces, we need to hold out a harness and separately test changes in tools, context management and repositories.

2. Solving a task and leaving a useful example are different achievements

First, a training task has to work. LegoFlow builds tasks from merged pull requests, reconstructs an execution environment, and checks that the original code fails relevant tests while the reference patch passes. SWE-Lego combines real issues with tasks created by injecting bugs, balancing complexity and scale. These checks remove unusable tasks; they still leave the question of whether the tests capture the full requirement.

Next comes the trajectory: what the teacher inspected, what it did, and how it checked the result. In Terminal-Lego, the teachers' own task performance did not predict how well students learned from them. Across the teacher and student combinations studied, traces that exposed an inspect-act-verify routine transferred better. A student needs access to the evidence behind an action. A sequence of correct commands can be a poor explanation of how to solve the next problem.

LegoFlow's data experiments also caution against treating reasoning length as quality. Removing the group with the shallowest reasoning improved student performance, while selecting progressively longer traces brought diminishing returns. This supports filtering examples that omit necessary analysis. It does not establish that extending an explanation will improve it. I would look for whether a trace explains consequential decisions and responds to new evidence.

Some successful traces need to be excluded for a simpler reason: the teacher found the reference patch in Git history or online. Such a trace can pass the tests without demonstrating the investigation we want to teach. Prompt instructions help, but the environment matters too: remove histories that reveal the answer, restrict external access during execution, and check the submitted changes independently. Trust in the data depends on those concrete conditions.

3. Decide what to teach, and record what actually happened

Supervised fine-tuning (SFT) learns from demonstrations, but every step in a demonstration need not be an imitation target. SWE-Lego's error masking keeps failed steps in context while excluding them from the imitation loss. The student can still see what failed and how the attempt recovered. A failure can be useful context without being an action we want the model to repeat.

Reinforcement learning (RL) uses task outcomes to update behavior. One complication is that a harness can compact or rewrite history, so a saved transcript may not reconstruct the input used at generation time. Lego-RL captures tokens, probabilities and mixture-of-experts routing as generation happens, then checks their correspondence on the training side. History rewrites still limit reconstruction, and high probability correlation does not imply numerical agreement everywhere. A healthy training curve cannot substitute for these checks.

Many useful tasks lack a single executable correctness check. RLVRR derives finer content and style rewards from reference answers. OVD uses text feedback from a black-box teacher to rank the student's own partial trajectories, retain better portions and replace weaker continuations. These methods widen the sources of supervision. They also make it worth checking whether improvement reflects the underlying task or closer agreement with the reference and evaluator's preferences.

Multimodal reasoning offers another reason to be specific about training objectives. Our study of long-CoT SFT and RL found that SFT helped difficult questions but encouraged verbosity, while RL gave more balanced gains and shorter answers. The combinations tested retained trade-offs. SRPO instead targets self-reflection, rewarding concise, useful corrections. These findings favor feedback aimed at a particular behavior; adding another training stage does not automatically add its benefits.

4. Check the result, and how it earned its score

A passing test is valuable evidence. Its meaning depends on the coverage of the tests, the clarity of the requirements and the integrity of grading. REAgent begins with requirements, organizing and refining the issue description before patch generation. SwingArena places patch submission and reviewer-written tests in continuous integration, studying issue resolution across long contexts and multiple languages.

SWE-Review asks what happens after submission. A reviewer explores the repository, diagnoses the issue and gives feedback on the candidate patch so the generator can revise it. We evaluate both the decision and whether the feedback helps resolve the issue. Independent investigation can still leave shared blind spots: generator and reviewer may miss the same edge case. Review and independent tests should therefore complement each other.

Recent benchmark maintenance makes this concern tangible. The October 2026 SWE-Bench Pro V2 paper documents repaired tasks and a hardened protocol: restrict network access, then reapply and grade the patch in a clean container. This echoes the answer leakage encountered in LegoFlow. More capable agents expose task defects and grading loopholes that earlier systems did not reach, so evaluation needs maintenance as capabilities change.

Scores also depend on resources. In Anthropic's February 2026 experiments, changing infrastructure allocations on Terminal-Bench 2.0 produced a six-percentage-point spread. That number belongs to the reported setup, but the implication for comparisons is broader: document CPU, memory, timeouts, network rules and retries. Otherwise, a small score difference is difficult to attribute to the model.

5. Images, the web and physical actions

Multimodal tasks make the evidence question particularly clear: did the agent perceive the clue it needed? MMSearch-Plus requires fine visual cues to be carried through iterative image-text search and cross-checking, with tools for marking, cropping and targeted retrieval. PhyX tests the combination of visual information, physics knowledge and real constraints. NAVERO uses descriptions with altered actions or relations to test fine distinctions in video understanding. Together they motivate separating perception, retrieval and reasoning failures when diagnosing an incorrect answer.

RoboCodeX decomposes high-level instructions into object-specific operations and generates control code. This makes the connection between plans, constraints and execution more explicit. Software habits cannot simply be carried over: physical actions may be irreversible, and when the system checks matters. Our survey of autoregressive models in vision maps the representation and generation methods; connecting these capabilities to reliable sustained action remains a further research problem.

6. The next step: building a project with its user

Extending a single repair run is only part of the challenge. NL2Repo-Bench starts with a requirements document and an empty workspace, asking agents to design the architecture, manage dependencies and implement an installable project. RoadmapBench studies multi-goal version upgrades in existing repositories. These settings expose premature stopping, inconsistent changes across files and plans that fail over time.

RPG / ZeroRepo explores structured planning that connects features, files, data flows and functions. It suggests a direction I would like to test: persistent project state that records accepted requirements, reasons for design decisions, verified functionality and unresolved assumptions. More conversation history alone does not ensure those distinctions survive. The records also need revision when a requirement or implementation changes; a stale plan can be as misleading as a forgotten one.

With the user involved, finishing autonomously is only one possible objective. UserSWE, released in October 2026, adds dynamic simulated users and execution checks at each turn, finding that agent rankings change with the interaction budget. Simulation cannot replace experiments with real users, but the result challenges the use of single-turn scores to describe collaboration. The timing of a question seems especially worth studying. Resolving an architectural ambiguity early could avoid substantial rework; asking something the agent could establish by reading the code may simply interrupt the user.

Long projects also inherit earlier design choices. SlopCodeBench has agents repeatedly extend their own code and tracks redundancy and concentrated complexity. It observes that passing checks can coexist with deteriorating structure. Delivery should leave a project that can accommodate the next change. That gives review a longer horizon too: did this patch break an earlier feature, lose an agreed requirement, or make the next feature harder to implement?

What I would test next

These are research directions suggested by the work above, rather than conclusions it has already established.

  1. Test project memory under changing requirements. Compare full conversation history, summaries, and explicit requirement and verification records on tasks with several requirement changes. Measure regressions, forgotten commitments and recovery after interruption alongside final success.
  2. Measure the value of a question together with its burden. With a fixed budget of user time, compare clarification, direct attempts and intermediate demonstrations. Question count alone is a poor measure of collaboration. The useful outcomes are fewer misunderstandings, less rework and less repeated explanation.
  3. Use the next change to assess the current delivery. After independent acceptance, add a related requirement and measure modification cost, regressions and structural changes. This tests whether the agent left a project that can keep developing, and connects directly to the cost of sustained work.

Questions still open

  • After implementation, testing and user discussion all contribute to an outcome, how can training identify the actions that made a difference?
  • When requirements change, how should an agent decide which earlier decisions to revisit and which work to preserve?
  • How can independent tests, code review and user acceptance complement each other without reducing project quality to a test pass rate?
