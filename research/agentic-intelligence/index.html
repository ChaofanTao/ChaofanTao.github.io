Agentic Intelligence

An agent's ability doesn't live in the model alone. It lives in the loop around it: seeing the situation, acting, learning from what happened, and being checked. This page walks through what we found, and shares some thoughts on what will come next.

By Chaofan Tao (陶超凡) · Last updated November 9, 2026

For a long time, progress in AI meant a better answer to a fixed, given question. Agents change the question: an agent has to notice the detail that matters, decide what to try, act, read what came back and adjust. Each of those steps can fail on its own, and each needs its own kind of evidence: whether the model saw the correct materials, whether its actions were grounded in what the environment showed it, whether it learned the right lesson from previous attempts, and whether we can trust the check that says it improved.

So far, coding agents are where we study all of these at once. Code leaves a record of every action and every result, and tests give an outcome you can verify. At LegoX, we build each part of this loop as open, reusable pieces: how verified experience is collected, how it becomes training signal, and how the result is checked. Our multimodal work asks the same questions where the environment is an image, a video, the web or a robot.

1. Coding agents as a typical agentic scenario

A coding agent never sees a repository directly. It sees whatever its harness shows it: which files and tool outputs reach the context, when history is compacted, how errors are reported, what happens after a command fails. When we trained the same starting model inside three widely used harnesses (OpenHands, Claude Code and OpenCode) with Lego-RL, it already behaved differently in each before any training. The harness is part of the environment, not plumbing around the model. That observation shaped how we collect data, how we train, and how we check results.

Data: experience worth learning from

LegoFlow abstracts and decouples complicated work into steps that can be verified. LegoFlow treats complicated engineering work that involves multiple repositories as a chain of blocks. Curator finds merged pull requests, gathers the issue, commits and tests, rewrites them into a task that does not leak the answer, builds an isolated environment and keeps the task only if the original code fails the tests and the reference fix passes. Because passing that check only makes a task usable, Curator also scores difficulty with a static rubric over the size of the patch, the logic it adds, how much of the codebase it touches, the tests and the detail of the instructions, with no LLM judge involved.

The whole pipeline can be run by an agent. Tracer rolls out trajectories in sandboxes and screens them, and Trainer and Evaluator close the loop. Every block is packaged as a plugin skill, so a coding agent such as Claude Code or Codex can run the pipeline itself, and each block has its own dashboard. In one experiment, an agent ran the whole pipeline end to end, read the evaluation, noticed that many teacher traces contained only shallow reasoning, changed the filter and trained a clearly better model in the next round.

SWE-Lego combines real tasks from resolved pull requests with synthetic ones created by injecting bugs, through LLM rewriting and syntax-tree transformations. Real tasks bring depth and realism; synthetic tasks bring scale, and for the same repositories, adding them keeps helping. Terminal-Lego brings the same discipline to command-line work, turning Stack Overflow problems into Docker-verified tasks.

The lessons that mattered most were about which trajectories to keep. Terminal-Lego found that the strongest solver is not necessarily the best teacher: traces that visibly inspect, act on what they found and then verify the result teach students better than traces from stronger agents that jump straight to the answer. LegoFlow found that reasoning depth matters more than coverage. Teachers that think a little on every turn teach less than teachers that think hard when the problem calls for it, and most of the benefit comes from removing the shallowest traces rather than keeping only the longest. SWE-Lego added practical cleaning rules: repair malformed tool calls, keep the tool set small, and recycle attempts that found the right file but failed to fix it.

Experience also has an honesty problem. Stronger teachers are better at finding shortcuts: locating the upstream pull request, copying the patch, or reading the fix from Git history. A successful trajectory is not necessarily an honest one. What worked was two layers: tell the agent plainly not to look up solutions, and make it impossible anyway, by rewriting Git history, hiding test files and restricting the network while the agent works, then restoring them only for grading.

Learning: turning experience into capability

Plain supervised fine-tuning works well when the loss gets as much care as the data. In SWE-Lego, error masking keeps the whole trajectory, mistakes included, in context but takes no gradient on the wrong steps, so the model learns from its errors without learning to repeat them. A curriculum uses trajectory length as a stand-in for difficulty and trains from easy to hard, carrying earlier data forward. At inference time, extra compute is best spent first on more interaction turns and, once that saturates, on parallel attempts, with a verifier that answers "yes" or "no" in text choosing among them better than a scoring head does.

For reinforcement learning, the trainer must see what the agent actually did. Lego-RL trains inside the real, native harness. Harnesses rewrite their own history by compacting context, re-serializing tool calls and running sub-agents, so a saved transcript is not the token sequence that was sampled. An in-process proxy records tokens, probabilities and mixture-of-experts routing at generation time, and the routing is replayed during training. Mismatches here make no noise: training runs and curves move, which is exactly why they have to be checked explicitly.

The runs themselves taught two more lessons. Tasks the model always or never solves teach it nothing, so the useful difficulty band has to follow the policy as it improves. And a falling reward can mean a broken parser or failed environment setups rather than a worse policy, so dashboards that break down how every attempt ended are part of the method, not an extra. After training, the agents read more code before editing, reread their own edits and run tests more often, at the cost of longer sessions.

Two follow-ups extend the recipe. Training one model on a mix of harnesses came close to the average of separately trained models while narrowing some of the gaps between harnesses. Single-rollout optimization learns from one attempt per task with a learned critic instead of comparing many attempts, which saves most of the sampling but only works once the critic has been warmed up and the advantages normalized; without that, the policy collapsed into repeating its "think" tool. For tasks without a single checkable answer, RLVRR builds a chain of rewards from good reference answers, covering content and style, and OVD learns from a teacher's text feedback on the student's own partial attempts, keeping good beginnings and replacing weak continuations.

Checking: review and evaluation

SWE-Review trains a reviewer agent that explores the repository on its own, works out the root cause, compares it with a submitted patch and writes structured feedback, turning one-shot generation into generate, review and revise. Two results matter beyond the paper: review data also makes models better at fixing issues, and because choosing among a few attempts is cheaper than producing many more, a good reviewer makes test-time compute go further. SwingArena puts models into a continuous-integration loop as both patch submitters and test-writing reviewers across several languages, and REAgent (ICSE 2027) checks and improves the issue description itself before any patch is written.

2. Beyond code: multimodal learning and the physical world

Code is a forgiving environment: everything is text and every result can be checked. Our multimodal work asks what the loop needs when the agent has to look. In NAVERO (arXiv 2024), we found that video-language models often can't tell who did what to whom, matching a video to a caption even when the action or relation is wrong; training on such near-miss descriptions taught the model to separate similar actions. PhyX shows models answering physics questions about images from memorized formulas and surface patterns rather than understanding the situation. MMSearch-Plus builds search tasks whose answers depend on small visual clues carried through several rounds of retrieval; tools to mark, crop and zoom change what the agent can find, and most failures come from not locating the right evidence rather than from the last reasoning step.

On training, the synergy dilemma (TMLR 2025) study found that long chain-of-thought SFT and RL help reasoning VLMs in different places, and that combining them tends to trade one benefit for the other. SRPO first shows the model what a useful reflection looks like, then rewards reflections that actually change its reasoning. RoboCodeX turns instructions into object-level actions with grasping and safety constraints written as code, so code plays for a robot the role a harness plays for a software agent. Our survey of autoregressive models in vision (TMLR 2025) maps how visual generation and understanding are converging, and its paper list has become a widely used reference.

Across these projects, the failure usually starts before the reasoning, at seeing the right detail or finding the right evidence. That is the part of the loop that agents, unlike fixed models, can go back and fix.

What we learned

  1. The strongest model is not necessarily the best teacher. What transfers is behavior the student can see and imitate: looking, acting on what was found, checking. The same mismatch between teacher strength and student learnability shows up in our distillation work.
  2. Reliable judgment is the scarce resource. Verified tasks, verifiers, reviewers and CI-based arenas are all ways of producing judgments we can trust. Generating attempts is cheap; choosing between them reliably is what scales.
  3. The trainer must see what the agent actually did. In agent RL, systems details such as token alignment and routing replay decide whether learning optimizes the right thing.
  4. Stronger agents find more shortcuts for hacking. Git history, upstream patches, visual questions answerable from text alone: honesty has to be built into the environment and the benchmark.
  5. Think in order to act. A reasoning step is worth what it does for the next action, not how long it is. Traces that inspect, act on what they found and then verify teach students more than traces from stronger agents that jump to the answer (Terminal-Lego: paper · code · data). Extra inference compute pays off first as more interaction turns, and only then as parallel attempts (SWE-Lego: paper · code · models and data). Rewarding reflections that change the reasoning works better than rewarding longer ones (SRPO: paper · code · data), and marking, cropping and zooming find visual evidence that more deliberation alone misses (MMSearch-Plus: paper · code · data). This is not a case for thinking less: teachers that think hard at the decisive step teach better than teachers that think a little everywhere (LegoFlow: blog · code · data). The point is to put thinking where the action needs it.

Some thoughts on the future

These are personal views. Each starts from a problem we have already met in small form in the work above.

Ultra-long-horizon agents: from hours of work to weeks

Agents are moving from tasks of hours to tasks of weeks: building a feature, migrating a codebase, running a research project. At that length, four problems we have seen in small form become central:

  • The goal drifts. REAgent showed that a vague issue misleads agents even on short tasks; a week-long task has to revisit its requirements as it goes.
  • One verdict at the end is too little feedback. Progress needs checking at milestones, the way SWE-Review checks a patch before it is accepted.
  • Credit is hard to assign. In single-rollout optimization, the critic's estimate tended to jump when new tool feedback arrived, a hint that credit can be anchored to meaningful checkpoints.
  • Environments will break. State has to survive failures, the lesson behind Lego-RL's failure dashboards and our fault-tolerant serving work.

Recording lessons is the subtle step. I think experience should be kept at levels: habits in the weights, procedures as reusable skills and tools (LegoFlow's blocks are a small example), and task-specific facts in memory, each tagged with the data, code version and settings under which it held.

Teams of agents: extra agents help only when they add independent evidence

SWE-Review works because the reviewer explores the repository itself rather than rereading the generator's reasoning; SwingArena separates patch writers from test writers. Two agents with the same context tend to miss the same bug, so I think teams should divide verification, not just labor, and share evidence and provenance, not only conclusions. Measuring that independence, when agents share a base model's blind spots, is still open; studies of why multi-agent systems fail point the same way.

Evaluation: treat it like a security boundary

Every capability gain we saw came with a gain in exploiting the environment. Benchmarks for strong agents need locked-down networks, clean re-grading, held-out tasks and regular refreshes, and training records should separate attempts that failed, were never scored, or "succeeded" by a route we would not accept.

AI for AI (or RSI): judgment will be the weakest link

AlphaEvolve shows that AI can already propose and test improvements to algorithms and infrastructure; LegoFlow's agent-run iterations are a small instance. Generating candidates is easy; deciding which are real is hard. A self-improving loop should propose, select and confirm on separate information and compare at equal total budget. The gains most likely to compound are to its own pipelines, environments and verifiers.

AI for Science: the longest horizon, with the weakest verifier

Science stretches everything above: horizons of months, goals that shift as you learn, and rarely a unit test for a claim. Simulators, analysis sandboxes and programmable labs will play the role that harnesses and tests play for code; AI for AI moves first because its lab is a compute cluster.

Two links to our work are direct (though definitely out of date :P). PhyX shows that multimodal models still lean on memorized formulas rather than physical understanding. Our vocabulary scaling study trusted its conclusion only after three independent methods agreed, the replication habit a science agent should have by default. And since the scientific form of reward hacking is cherry-picking runs, I expect useful science agents to log every experiment, not just the successes, and confirm findings on settings never used in the search. A cheap, hard-to-fool check for a scientific claim is, to me, the central open problem.

Open questions

Questions I find interesting, some raised by our own work and some by where the field is now.

  • Is the harness part of an agent's skill, or something it should generalize across? The same model already behaves differently across harnesses before training. Should agents be harness-agnostic, co-designed with one harness, or able to adapt to a new one on the fly?
  • Will scaling RL environments look like scaling pre-training data? Verified environments are now the scarce input. Does capability keep growing with more and more varied environments, or does a small number that are hard in the right way matter more?
  • Can supervision keep up with what agents can do? The length of tasks agents can complete keeps growing, while human review does not scale and scalable oversight remains unsolved. If reviewers come from models similar to the policy, the gap between generating and verifying may be the real ceiling on self-improvement.
  • How should an agent learn on the job? Lessons from deployment reach the weights only through occasional retraining. Updating habits without forgetting, and keeping memory correct as code and data change, would change what deploying an agent means.
  • When should an agent stop and ask a person? A long-running agent has to judge when a requirement is too ambiguous, or an action too risky, to continue alone. Asking too often wastes people's time; asking too rarely wastes weeks of work, and today this is barely measured.
  • Does multimodal perception need to become active? Our multimodal failures usually start before reasoning, at seeing the right detail. Will scale fix this, or must agents look again, zoom and gather evidence as part of reasoning, on screens and in the physical world?
