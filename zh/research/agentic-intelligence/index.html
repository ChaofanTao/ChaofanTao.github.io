智能体的学习、协作与自我改进

智能体的能力不只在模型里，而在模型周围的那个循环里：看清情况、动手去做、从结果中学习、再接受检验。我们在 LegoX 为代码智能体开源搭建这个循环，多模态方向的工作则检验它在代码之外还需要什么。这篇文章讲讲我们发现了什么，以及我认为这个循环接下来该往哪里走。

作者：陶超凡（Chaofan Tao） · 最后更新 2026-11-09

很长一段时间里，AI 的进步意味着对一个固定的问题给出更好的答案。智能体改变了问题本身：它要注意到关键的细节，决定先试什么，动手，读懂返回的结果，再调整做法。每一步都可能单独出错，每一步也需要不同的依据：模型是否看清了该看的东西，它的行动是否建立在环境真实反馈的基础上，它能否从一次尝试中学到正确的东西，以及我们能否相信那个“它进步了”的判断。

代码智能体让我们可以同时研究这几件事。代码会记录下每一次操作和每一个结果，测试又能给出可以核对的结论。在 LegoX，我们把这个循环的每一部分都做成开放、可复用的组件：可验证的经验怎么收集，怎么变成训练信号，结果又怎么检验。多模态方向的工作则在图像、视频、网页和机器人这些环境里，追问同样的问题。

1. 把代码智能体当作实验室

代码智能体从来不会直接看到代码仓库，它看到的是 harness 让它看到的东西：哪些文件和工具输出会进入上下文，历史什么时候被压缩，报错怎么呈现，命令失败后接下来怎么走。我们用 Lego-RL 把同一个初始模型放进三个常用的 harness（OpenHands、Claude Code、OpenCode）里，还没开始训练，它在三个环境中的表现就已经不一样了。harness 是环境的一部分，而不是模型外面的配套设施。这个观察影响了我们怎么收集数据、怎么训练、怎么检验结果。

数据：收集值得学习的经验

LegoFlow 把代码数据工程拆成一串模块。Curator 寻找已合并的 PR，收集对应的 issue、提交和测试，改写成不泄露答案的任务，搭建独立的运行环境，并且只保留“原代码测试不通过、参考修复测试通过”的任务。通过这一步只说明任务能用，所以 Curator 还用一套静态规则给任务打难度分，看补丁有多大、加了多少新逻辑、牵涉代码库的范围有多广、测试有多复杂、需求写得有多详细，全程不依赖 LLM 打分。Tracer 在沙箱里生成并筛选轨迹，Trainer 和 Evaluator 完成训练和评测。每个模块都封装成插件 skill，Claude Code、Codex 这样的代码智能体可以自己运行整条流水线，每个模块也都有自己的看板。在一次实验里，智能体端到端地跑完了整个流程，读完评测结果后发现很多老师轨迹的推理过于浅显，于是调整了筛选规则，下一轮训练出的模型明显更好。

SWE-Lego 把来自真实 PR 的任务，和通过 LLM 改写、语法树变换人为注入 bug 生成的任务结合起来。真实任务更真实、更有深度，合成任务提供规模；在同样的代码仓库上，加入合成任务会持续带来提升。Terminal-Lego 把同样的严格要求用到命令行任务上，把 Stack Overflow 上的问题变成经过 Docker 验证的任务。

最重要的经验，是关于该留下哪些轨迹。Terminal-Lego 发现，最会解题的模型不一定是最好的老师：那些先观察、根据看到的情况动手、最后检查结果的轨迹，教出来的学生比更强模型直接给答案的轨迹更好。LegoFlow 发现，推理的深度比覆盖面更重要：每一步都想一点的老师，不如在关键步骤上认真想的老师；而且大部分好处来自去掉最“浅”的那部分轨迹，而不是只留下最长的。SWE-Lego 还总结了几条实用的清洗规则：修正格式错误的工具调用，精简工具集，并回收那些找对了文件却没修好的尝试。

经验还有一个“诚实”的问题。越强的老师越会走捷径：找到上游的 PR、直接复制补丁，或者从 Git 历史里翻出答案。成功的轨迹，不一定是老老实实解出来的。有效的做法是两层防护：一方面在提示里明确告诉智能体不要去查现成答案；另一方面在环境里让它根本查不到，在智能体工作时改写 Git 历史、隐藏测试文件、限制网络，只有评分时才恢复。

学习：把经验变成能力

SWE-Lego 证明，只要像对待数据一样认真对待损失函数，单靠 SFT 也能训练出很强的开源代码智能体。错误掩码让模型看到包括错误在内的完整轨迹，但不在错误步骤上计算梯度，这样它能从错误中吸取教训，却不会学着重复错误。课程学习用轨迹长度粗略代表难度，从易到难地训练，并在后面的阶段保留前面的数据。推理时多出来的算力，最好先花在增加交互轮数上，饱和之后再用于并行尝试；在多个尝试中挑选时，直接用文字回答“是”或“否”的验证器比打分头更准。

在强化学习方面，Lego-RL 直接在真实、未改动的 harness 里训练。难点在于保证训练时看到的就是智能体当时真正做的。harness 会压缩上下文、重新序列化工具调用、运行子智能体，悄悄改写自己的历史，所以保存下来的对话并不等于实际采样的 token 序列。一个进程内代理在生成时记录 token、概率和混合专家模型的路由，训练时再按原样回放路由。这类不一致不会发出任何警告：训练照常进行，曲线照常变化，所以必须专门检查。训练过程本身还带来两条经验：模型总能做对或总是做错的任务，对它来说什么也学不到，所以“刚好够得着”的难度区间要跟着模型的进步调整；奖励下降也可能是解析器出错或环境搭建失败，而不是模型变差了，所以拆解每次尝试如何结束的看板，是方法的一部分，而不是锦上添花。训练之后，智能体会在改代码前读更多代码、改完回头检查、也更常跑测试，代价是每次交互的时间更长。

在此基础上还有两个延伸。用一个模型同时在多个 harness 上训练，效果接近分别训练的平均水平，还缩小了不同 harness 之间的部分差距。单 rollout 优化借助一个学出来的 critic，每个任务只尝试一次就能学习，省掉了大部分采样；但前提是 critic 先充分“热身”、优势值做好归一化，否则模型会退化成反复调用 think 工具。对于没有唯一标准答案的任务，RLVRR 从优质参考答案中构造一组兼顾内容和风格的奖励，OVD 则用老师对学生部分回答的文字评价来指导学习，保留写得好的开头，替换写得差的后半段。

检验：审查与评测

SWE-Review 训练了一个审查智能体：它自己去翻代码仓库、找出问题根源，再和提交的补丁对照，写出有条理的反馈，把“一次写完就交”变成“写、审、改”。有两个结论超出了这篇论文本身：审查数据反过来也能让模型更会修 bug；而且从几个尝试里挑一个，比再多生成很多个更便宜，所以一个好的审查者能让推理时的算力发挥更大作用。SwingArena（ICLR Oral）把模型放进持续集成流程，让它们在多种编程语言中轮流提交补丁和编写测试；REAgent（ICSE）则在写补丁之前，先检查并完善 issue 描述本身。

2. 走出代码：多模态推理与真实世界

代码是一个很宽容的环境：一切都是文本，每个结果都能核对。多模态方向的工作要问的是，当智能体必须“看”的时候，这个循环还需要什么。在 NAVERO 里，我们发现视频语言模型常常分不清是谁对谁做了什么，即使描述里的动作或关系是错的，也会把视频和描述配对成功；用这类“差一点就对”的描述来训练，模型才学会区分相似的动作。PhyX 发现，模型回答关于图片的物理问题时，常常靠背下来的公式和表面特征，而不是真正理解当时的情况。MMSearch-Plus 设计的搜索任务，答案依赖图里的细小线索，而且要经过几轮检索才能用上；给智能体配上标记、裁剪、放大的工具，会改变它能找到什么，而失败大多是因为没找到对的证据，不是最后一步推理出错。

在训练方面，“协同困境”研究发现，长思维链 SFT 和 RL 对视觉语言模型推理的帮助落在不同的地方，组合起来往往是用一种好处换另一种。SRPO 先让模型看看有用的反思长什么样，再奖励那些真正改变了推理的反思。RoboCodeX 把指令拆成针对具体物体、考虑抓取和安全的动作，并写成代码，代码对机器人的作用，就像 harness 对软件智能体的作用。我们的视觉自回归模型综述梳理了视觉生成与理解如何逐渐融合，配套的论文列表也成了很多人常用的参考。这些项目放在一起，总是指向同一个地方：问题往往在推理之前就出现了，出在没看清关键细节、没找到对的证据，而这恰恰是智能体能够自己去看、去补救的部分。

我们的体会

  1. 最强的模型往往不是最好的老师。真正能传下去的，是学生看得见、学得来的做法：先看，再根据看到的动手，最后检查。老师强弱和学生能否学会之间的错位，在我们的蒸馏工作里也出现过。
  2. 真正稀缺的是可靠的判断。可验证的任务、验证器、审查者、基于持续集成的评测，本质上都是在产出可以信任的判断。生成答案很便宜，可靠地从中挑选才是能做大的部分。
  3. 训练时看到的，必须是智能体当时真正做的。在智能体强化学习里，token 对齐、路由回放这些系统细节，决定了学习是否朝着正确的方向走。
  4. 越强的智能体，越会找捷径。Git 历史、上游补丁、不看图也能答对的视觉题，要保证诚实，必须靠环境和评测本身的设计。
  5. 想得深比想得多更重要。在需要的地方认真推理，有用的反思胜过冗长的反思，证据胜过篇幅。

我对接下来的判断

上面这些项目，在某种意义上是整个领域正在更大规模上面对的问题的缩小版。下面是我认为它们会通向哪里。

更长的任务：难点从“收集经验”变成“留住经验”

当任务从修一个 bug 变成开发一个功能，甚至连续几天推进一个研究项目，难的不再是攒更多经验，而是留住其中真正有用的部分。我们的数据工作已经显示出这个方向：深度胜过覆盖面，脚踏实地的轨迹胜过看似自信的轨迹，部分成功的尝试和审查意见里也有有用的教训。我认为经验需要分三层保存。稳定的习惯，比如改完代码回头检查，应该进入模型权重；做事的流程，比如如何搭建和验证一个环境，应该沉淀为可复用的技能和工具，LegoFlow 的模块就是一个小例子；具体任务中的事实，应该进入记忆，而且每条记忆都要记下它成立的条件：用的是哪份数据、哪个代码版本、什么设置。没有这些条件，长期运行的智能体会不断复用早已悄悄失效的结论。

多个智能体协作：只有带来独立的证据，多一个智能体才有用

让更多智能体并行工作，是很自然的扩展思路。但我们的审查工作提示了一个更具体的条件。SWE-Review 之所以有效，是因为审查者自己去探索代码仓库，而不是重读生成者的思路；SwingArena 也把写补丁的和写测试的分成两个角色。两个上下文相同、假设相同的智能体，往往会漏掉同一个 bug。所以我认为，有用的团队应该按“分工验证”来组织，而不仅仅是“分工干活”：提出方案的、做测试的和做审查的各自看到不同的信息；共享的记忆要记录证据和来源，而不只是结论。关于多智能体系统为什么会失败的研究也指向同一个方向：很多失败来自需求不清楚、验证不到位，以及智能体不知道什么时候该停下来。

评测：它正在成为主要瓶颈，必须像安全防线一样对待

我们看到的每一次能力提升，都伴随着利用环境漏洞的能力同步提升。在 LegoFlow 里，越强的老师越会作弊；在 Lego-RL 里，沙箱的每个阶段都需要防护；在多模态评测里，有些题不认真看图也能答对。我预计这个问题会越来越严重。给强智能体用的评测，需要封锁网络、在干净的环境里重新评判最终补丁、保留从不在开发中使用的测试任务，并定期更新。训练奖励也需要同样的严谨：记录里要分清一次尝试是失败了、根本没被评分，还是用我们不认可的方式“成功”了，因为混淆这些情况的流程，会把错误的教训传给下一个模型。

AI 改进 AI：最薄弱的一环会是判断

AlphaEvolve 这样的系统已经表明，AI 可以提出并检验对算法和计算基础设施的改进。LegoFlow 由智能体主导的迭代就是同一思路的一个小例子：智能体读评测结果、调整训练数据的筛选方式，下一个模型随之变好。从我们的经验看，生成候选改进是容易的部分，难的是判断哪些改进是真的。一个自我改进的循环，应该把“提出改进”“挑选改进”和“确认改进”所用的信息分开；保留从未参与搜索的新任务；并在相同的总预算下比较进展，免得“更好”只是“搜得更多”。我还认为，最可能持续积累的，是对循环自身工具的改进，也就是数据流水线、运行环境和验证器，因为它们每改进一次，后面每一轮的质量都会跟着提高。

还没解决的问题

  • 在多个 harness 上训练过的智能体，换到一个从没见过的 harness 里，还能表现好吗？
  • 当成功或失败要在几个小时的操作之后才揭晓，我们怎么知道是哪些步骤真正起了作用？
  • 需要长期保留的经验，应该怎样在权重、技能和记忆之间分配？
  • 一个自我改进的循环，怎样证明后面几轮发现改进的效率真的提高了，而不只是试了更多候选？
