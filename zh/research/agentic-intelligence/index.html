智能体的学习、协作与自我改进

智能体的本事不全在模型里，更在模型外面那一圈循环里：看清情况，动手去做，从结果里学，再接受检验。我们在 LegoX 为代码智能体开源搭建这个循环，多模态方向的工作则在检验：离开代码，这个循环还缺什么。这篇文章聊聊我们发现了什么，也谈谈我对接下来的一些想法。

作者：陶超凡（Chaofan Tao） · 最后更新 2026-11-09

很长时间里，AI 的进步就是对一个固定的问题答得更好。智能体把问题本身变了：它得注意到要紧的细节，想好先试什么，动手，看懂返回的结果，再调整。每一步都可能单独出错，每一步要的证据也不一样：模型有没有看到该看的东西，它的动作是不是基于环境真实的反馈，它能不能从一次尝试里学到对的东西，还有，我们凭什么相信“它变强了”。

代码智能体让我们能把这几件事放在一起研究。代码会留下每一步操作和每一个结果，测试又能给出可以核对的结论。在 LegoX，我们把这个循环拆开，每一块都做成开放、可复用的组件：可验证的经验怎么收集，怎么变成训练信号，训练结果又怎么检验。多模态方向的工作，则是在图像、视频、网页和机器人这些环境里问同样的问题。

1. 把代码智能体当作实验室

代码智能体从来看不到代码仓库本身，它看到的是 harness 给它看的东西：哪些文件和工具输出会进上下文，历史什么时候被压缩，报错长什么样，命令失败以后接着怎么走。我们用 Lego-RL 把同一个初始模型分别放进三个常用的 harness（OpenHands、Claude Code、OpenCode），还没开始训练，它在三处的表现就已经不一样了。也就是说，harness 本身就是环境的一部分，不是模型外面的配套设施。这一点决定了我们后来怎么收数据、怎么训练、怎么检验。

数据：收集值得学的经验

LegoFlow 把已合并的 PR 变成经过验证的任务。LegoFlow 把代码数据工程拆成一串积木。Curator 去找已经合并的 PR，把对应的 issue、提交和测试收齐，改写成不会泄露答案的任务，搭好独立的运行环境，并且只留下“原代码测试不过、参考修复测试能过”的任务。能过这一关只说明任务可用，所以 Curator 还会用一套固定规则给任务打难度分：补丁有多大，加了多少新逻辑，牵动了代码库多大范围，测试有多复杂，需求写得多细，全程不用 LLM 打分。

整条流水线可以交给智能体自己跑。Tracer 在沙箱里跑出轨迹并做筛选，Trainer 和 Evaluator 负责训练和评测。每块积木都封装成插件 skill，Claude Code、Codex 这样的代码智能体可以自己把整条流水线跑起来，每块积木也都有自己的看板。有一次实验，智能体从头到尾跑完整个流程，读完评测结果后发现不少老师轨迹的推理很浅，就改了筛选规则，下一轮训出来的模型明显更好。

SWE-Lego 把两类任务放在一起用：一类来自真实的 PR，另一类是用 LLM 改写或语法树变换故意埋进 bug 造出来的。真实任务够真、够深，合成任务管够量；在同一批代码仓库上，加进合成任务会一直带来提升。Terminal-Lego 把同样严格的要求用到命令行任务上，把 Stack Overflow 上的问题做成经过 Docker 验证的任务。

最要紧的经验，是该留下哪些轨迹。Terminal-Lego 发现，最会解题的模型不一定是最好的老师，好老师是最适配学生能力的那一个：先观察、再根据看到的情况动手、最后检查结果的轨迹，教出来的学生比更强模型一步到位给出答案的轨迹更好。LegoFlow 发现，想得深比想得广更重要：每一步都浅浅想一下的老师，不如在关键处认真想的老师；而且大部分收益来自去掉最浅的那批轨迹，而不是只留最长的。SWE-Lego 还总结了几条很实用的清洗规则：修好格式出错的工具调用，工具集尽量精简，那些找对了文件却没改对的尝试也别扔，回收再用。

经验还有个“老不老实”的问题。老师越强，越会走捷径：找到上游的 PR 直接抄补丁，或者从 Git 历史里翻出答案。成功的轨迹，不一定是老老实实做出来的。管用的办法是两层防护：一是在提示里明说不许去查现成答案；二是在环境里让它根本查不到，智能体干活时改写 Git 历史、藏起测试文件、限制网络，等到评分时才恢复。

学习：把经验变成能力

只要像打磨数据一样打磨损失函数，单靠 SFT 也能走得很远。在 SWE-Lego 里，错误掩码让模型看到包括错误在内的完整轨迹，但出错的那几步不算梯度，这样它能从错误里长记性，又不会学着再犯。课程学习拿轨迹长度粗略代表难度，由易到难地训，后面阶段继续带着前面的数据。推理时多出来的算力，最好先花在多给几轮交互上，加到头了再用来并行多试几次；从几次尝试里挑结果时，直接用文字回答“是”或“否”的验证器，比打分头挑得更准。

做强化学习，训练时看到的必须是智能体当时真正做的。Lego-RL 直接在真实、原封不动的 harness 里训练。harness 会压缩上下文、重新序列化工具调用、跑子智能体，等于悄悄改写了自己的历史，所以存下来的对话记录并不等于当时实际采样出的 token 序列。我们用一个进程内代理在生成时就记下 token、概率和混合专家模型的路由，训练时再按原样回放路由。这类对不上的问题不会报任何错：训练照跑，曲线照动，所以必须专门去查。

训练本身还教会我们两件事。模型总能做对或总做不对的任务，对它来说学不到东西，所以“跳一跳够得着”的难度区间要跟着模型的进步往上挪。奖励往下掉，也可能是解析器坏了或者环境没搭起来，不一定是模型变差了，所以把每次尝试为什么结束拆开来看的看板，是方法的一部分，不是锦上添花。训练之后，智能体改代码前会多读代码，改完会回头检查，也更常跑测试，代价是每次交互的时间更长。

在这个基础上又往前走了两步。让一个模型同时在多个 harness 上训练，效果接近分开训练的平均水平，还缩小了不同 harness 之间的一部分差距。单 rollout 优化借助一个学出来的 critic，每个任务只试一次就能学，省掉了大部分采样；前提是 critic 要先充分“热身”，优势值也要做好归一化，不然模型会退化成一遍遍调用 think 工具。对于没有唯一标准答案的任务，RLVRR 从优质参考答案里构造一串兼顾内容和风格的奖励；OVD 则让老师对学生写了一半的回答给出文字点评，好的开头留下，写差的后半段换掉。

检验：审查与评测

SWE-Review 训练了一个审查智能体：它自己去翻代码仓库，找出问题的根源，再拿去和提交的补丁对照，写出有条理的反馈，把“一次写完就交”变成“写、审、改”。有两个结论不止对这篇论文有意义：审查数据反过来也能让模型更会修 bug；从几次尝试里挑一个，比再多生成很多次便宜，所以好的审查者能让推理时的算力更值钱。SwingArena 把模型放进持续集成流程，让它们在多种编程语言里轮流提交补丁、编写测试；REAgent 则在写补丁之前，先检查并补全 issue 描述本身。

2. 走出代码：多模态推理与真实世界

代码是个很宽容的环境：一切都是文本，每个结果都能核对。多模态方向要问的是，智能体必须用眼睛“看”的时候，这个循环还需要什么。在 NAVERO 里，我们发现视频语言模型常常分不清谁对谁做了什么，描述里的动作或关系明明是错的，它照样把视频和描述配上对；拿这类“只差一点”的描述来训练，模型才学会分辨相近的动作。PhyX 发现，模型回答图片里的物理问题时，常常靠背熟的公式和表面线索，并没有真正看懂当时的情形。MMSearch-Plus 设计的搜索任务，答案藏在图里的细小线索中，还要经过好几轮检索才用得上；给智能体配上标记、裁剪、放大这些工具，它能找到的东西就不一样了，而失败大多是因为没找到对的证据，而不是最后一步推理出了错。

训练方面，“协同困境”这项研究发现，长思维链 SFT 和 RL 对视觉语言模型推理的帮助落在不同地方，硬把两者叠在一起，往往是拿一种好处换另一种。SRPO 先让模型看看有用的反思是什么样子，再奖励那些真正改变了推理的反思。RoboCodeX 把指令拆成落到具体物体上、考虑了抓取和安全的动作，再写成代码；代码之于机器人，就像 harness 之于软件智能体。我们的视觉自回归模型综述梳理了视觉生成和理解是怎么慢慢走到一起的，配套的论文列表也成了不少人常翻的参考。

这些项目放在一起看，问题往往在推理之前就出现了：没看清关键细节，没找到对的证据。而这恰恰是智能体可以自己回头再看、再补的地方。

我们的体会

  1. 最强的模型，往往不是最好的老师。真正传得下去的，是学生看得见、学得来的做法：先看，再根据看到的动手，最后检查。老师强弱和学生学不学得会之间的错位，在我们的蒸馏工作里也出现过。
  2. 真正稀缺的是靠得住的判断。可验证的任务、验证器、审查者、基于持续集成的评测，说到底都是在产出可以信任的判断。生成答案很便宜，能可靠地从中挑出好的，才是能做大的部分。
  3. 训练时看到的，必须是智能体当时真正做的。在智能体强化学习里，token 对齐、路由回放这些系统细节，决定了学习是不是在朝对的方向走。
  4. 智能体越强，越会找捷径。Git 历史、上游补丁、不看图也能答对的视觉题，想要诚实，只能靠环境和评测本身的设计来保证。
  5. 想得深比想得多更重要。该用力的地方认真推理，有用的反思胜过冗长的反思，证据胜过篇幅。

对未来的一些思考

下面是我个人的看法。每一条都从上面工作里碰到过的小问题出发，看它放大之后会变成什么样。

超长程智能体：从几小时的活，到几周的活

智能体正在从几小时的任务，走向几周的任务：做一个完整的功能，迁移一个大代码库，推进一个研究项目。到了这个长度，我们在小任务里见过的四个问题会变成主要矛盾：

  • 目标会跑偏。REAgent 发现，哪怕是短任务，issue 写得含糊也会把智能体带偏；几周的任务更得边做边回头看需求。
  • 只在最后给一次“过”或“不过”，反馈太少。进展要在一个个里程碑上检查，就像 SWE-Review 在补丁合入前先审一遍。
  • 功劳很难分清。在单 rollout 优化里，critic 对成败的估计常常在新的工具反馈进来时跳一下，说明功劳也许可以记在关键节点上。
  • 环境一定会出故障。状态得扛得住失败，这和 Lego-RL 拆解失败原因的看板、我们容错推理服务的工作是同一个道理。

我的猜测是，这样的智能体会按里程碑来干活：每到一个里程碑，重读一遍目标，核实一下进展，把学到的东西连同条件记下来，再把当前状态存好。

“记下经验”这一步最讲究。我觉得经验要分三层存：习惯进权重，比如改完代码回头检查；流程做成可复用的技能和工具，LegoFlow 的积木就是个小例子；具体事实写进记忆，而且每条都要注明它在什么数据、什么代码版本、什么设置下成立。

多智能体协作：多一个智能体，得多带来一份独立的证据

SWE-Review 之所以有用，是因为审查者自己去翻代码仓库，而不是把生成者的思路再读一遍；SwingArena 也把写补丁和写测试分给了两个角色。上下文一样的两个智能体，往往会漏掉同一个 bug。所以我觉得，好的团队应该“分头验证”，而不只是“分头干活”，共享的记忆里也要记下证据和来源，而不只是结论。关于多智能体系统为什么会失败的研究，也指向同一个方向。

评测：得像守安全防线一样对待

我们看到的每一次能力提升，都伴随着钻空子的本事一起涨：老师越强越会作弊，沙箱的每个阶段都得设防。给强智能体用的评测，要封锁网络、在干净环境里重新评判、留一批开发中从不碰的任务，还要定期更新。训练记录也得分清：一次尝试是失败了、根本没评上分，还是用我们不认可的方式“成功”了。

AI 改进 AI：最薄弱的一环会是判断

AlphaEvolve 已经表明，AI 可以提出并检验对算法和基础设施的改进；LegoFlow 里由智能体主导的迭代，是同一个思路的小例子。想出候选改进容易，难的是判断哪些是真的。所以自我改进的循环应该把“提出”“挑选”“确认”用到的信息分开，留一批从没参与过搜索的新任务，并且在相同的总预算下比较。最可能越滚越大的，是对循环自身工具的改进：数据流水线、运行环境和验证器。

AI for Science：最长的周期，最弱的验证

科学研究把上面所有问题都放大了：周期以月计，目标会随着认识变化，而且几乎没有一个单元测试能告诉你某个结论对不对。模拟器、数据分析沙箱和可编程的实验室，会扮演代码世界里 harness 和测试集的角色；AI 改进 AI 之所以走在前面，是因为它的“实验室”就是计算集群。

和我们工作直接相关的有两点。PhyX 显示，今天的多模态模型还在靠背公式，而不是真懂物理。我们的词表缩放研究，是等三种互相独立的方法得出一致结论后才下判断的，这种“先复现、再相信”的习惯，科学智能体应该默认就有。另外，奖励投机在科研里的样子，就是只挑好看的实验来报，所以我预计有用的科学智能体会把试过的每个实验都记下来，不只是成功的那些，并且在搜索时没用过的设置上再确认一遍。

还没解决的问题

  • 在多个 harness 上训过的智能体，换到没见过的 harness 还行吗？我们的混合训练只能说明技能可以共享，还不能说明能迁移。打算怎么验证：训练时完全留出一个 harness，只拿它来测，轮流换着留。
  • 结果要几天后才揭晓，功劳怎么分？critic 在轮次交替处的跳变，暗示功劳可以按里程碑来分。打算怎么验证：同样的长任务、同样的算力，比较“在验证过的里程碑上给奖励”和“只在最后给一次奖励”。
  • 长任务怎么守住正确的目标？REAgent 在动手前把需求理清，可长项目里需求本身会变。打算怎么验证：在长任务中途改需求，看智能体能不能发现、多快发现。
  • 哪些该进权重，哪些做成技能，哪些记在记忆里？每种放法在底座模型更新后的表现都不一样。打算怎么验证：把同一条经验分别用三种方式存下来，换上更新的底座模型，看哪种还管用。
  • 自我改进的循环，怎么证明自己“改进的本事”变强了？新任务会被一轮轮用掉，等预算比较又很贵。打算怎么验证：记录每一轮要花多少预算，才能在一批从没碰过的任务上确认一次真改进；循环真在变强的话，这个数应该越来越小。
  • 一个科学结论的“单元测试”是什么？模拟可以被钻空子，真实实验又慢。打算怎么验证：先从模拟和便宜实验能互相核对的领域做起，看模拟里成立的发现，有多少能经得住真实检验。

    Shiqi Kuang, Zhao Tian, Kaiwei Lin, Chaofan Tao, Shaowei Wang, Haoli Bai, Lifeng Shang, Junjie Chen

    REAgent 先把问题描述整理成明确的需求，找出遗漏和含糊之处，再逐步补全，用来指导代码修复。研究关注的是：需求是否清楚，会怎样影响补丁质量。

  2. SWE-Lego: Pushing the Limits of Supervised Fine-tuning for Software Issue Resolving

    arXiv · 2026

    Chaofan Tao, Jierun Chen, Yuxin Jiang, Kaiqi Kou, Shaowei Wang, Ruoyu Wang, Xiaohui Li, Sidi Yang, Yiming Du, Jianbo Dai, Zhiming Mao, Xinyu Wang, Lifeng Shang, Haoli Bai

    SWE-Lego 研究仅靠监督微调能把代码修复做到什么程度。它结合真实与合成任务，保留错误作为上下文但不模仿错误步骤，并按难度安排训练，再用验证器选择候选补丁。

  3. LEGO-RL: Harness-Native Reinforcement Learning for Coding Agents

    arXiv · 2026

    Yiming Du, Yuxin Jiang, Tao Yuan, Jianbo Dai, Shaowei Wang, Jierun Chen, Chaofan Tao, Xianzhi Yu, Lifeng Shang, Kam-Fai Wong, Xiaohui Li, Haoli Bai

    LEGO-RL 让代码智能体在原有运行框架中接受强化学习。它记录生成时的信息、检查训练与运行是否对应，并通过隔离环境、评分保护和逐次尝试的诊断，减少错误训练信号。

  4. SWE-Review: Closing the Loop on Issue Resolution with Agentic Code Review

    Ruoyu Wang, Jierun Chen, Shaowei Wang, Chaofan Tao, Sidi Yang, Yuxin Jiang, Kim-Hui Yap, Lifeng Shang, Xiaohui Li, Haoli Bai

  5. What Makes Interaction Trajectories Effective for Training Terminal Agents?

    arXiv · 2026

    Sidi Yang, Chaofan Tao, Jierun Chen, Tiezheng Yu, Ruoyu Wang, Yuxin Jiang, Yiming Du, Wendong Xu, Jing Xiong, Taiqiang Wu, Lifeng Shang, Xiaohui Li, Ngai Wong, Haoli Bai

    Terminal-Lego 把真实问题转成可运行、可检查的终端任务。实验发现，解题更强的教师未必教得更好；明确展示查看信息、行动和验证过程的记录，更有利于学生迁移到新任务。

  7. MMSearch-Plus: Benchmarking Provenance-Aware Search for Multimodal Browsing Agents

    ICLR · 2026

    Xijia Tao, Yihua Teng, Xinxing Su, Xinyu Fu, Jihao Wu, Chaofan Tao, Ziru Liu, Haoli Bai, Rui Liu, Lingpeng Kong

    MMSearch-Plus 包含 311 个图文搜索任务，要求从图像细节出发，经过多轮检索与交叉核对找到答案。配套工具支持标记、裁剪和定向搜索，帮助检查视觉线索是否真正参与了解题。

  8. OVD: On-policy Verbal Distillation

    arXiv · 2026

    Jing Xiong, Hui Shen, Shansan Gong, Yuxin Cheng, Jianghan Shen, Chaofan Tao, Haochen Tan, Haoli Bai, Lifeng Shang, Ngai Wong

    OVD 不要求教师提供每个 token 的概率，而是用教师的文本评分评价学生生成的片段，保留较好的部分、替换较差的后续内容。它在网页问答与数学实验中研究这种反馈能否帮助学生学习。
